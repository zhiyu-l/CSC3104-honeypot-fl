# Process real replay logs for the ML team

This guide covers explicit replay selection. For the combined midnight CronJobs
that automatically process all completed sessions, follow [the nightly guide](cowrie-nightly.md).

The operator owns this path:

```text
Selected, completed replay sessions on each organisation's Cowrie PVC
    -> shared Kaggle feature extractor -> sessions.csv + manifest.json
    -> that organisation's S3 processed/replay/<run-id>/ folder
    -> ML team downloads and evaluates
```

The Kaggle training split remains the ML team's input for training. This job
processes new logs produced by replaying held-out attacks against Cowrie. It
does not replay attacks, create the Kaggle split, train models, or automatically
identify replay traffic among ordinary SSH tests.

## 1. Agree on the replay selection

Ask the replay owner for the **new Cowrie session IDs and pod UIDs** generated by
their completed replay, and the original dataset session IDs/expected labels if
available. Original Kaggle IDs alone cannot select new Cowrie sessions. Keep
the same extractor/schema revision for training and evaluation.

Create one selection file per organisation under ignored `.local/cowrie/replay/`.
Copy `services/log-processor/replay-selection.example.json`, replace the
placeholders, and add one entry per selected session:

```json
{
  "manifest_version": 1,
  "organisation": "orga",
  "run_id": "replay-001",
  "sessions": [
    {
      "pod_uid": "11111111-1111-1111-1111-111111111111",
      "session_id": "NEW_COWRIE_SESSION_ID",
      "source_session_id": "original-sensor:original-session",
      "expected_label": "recon"
    }
  ]
}
```

The IDs above illustrate the format; replace them with real replay identifiers.
`source_session_id` and `expected_label` are optional. Never label smoke tests
as held-out evaluation data. A selected session must contain exactly one connect
and one close event. Keep all its rotated files on the PVC until processing ends.
Use a new run ID (1–36 lowercase letters/digits/hyphens) for each publication.

To match a current pod name to its UID:

```powershell
kubectl --context kind-orga-honeypot-cluster -n default get pods -l app=cowrie -o custom-columns=NAME:.metadata.name,UID:.metadata.uid
```

The `session` field in Cowrie JSON is the session ID; the PVC directory is the
pod UID. Record this mapping during replay, before autoscaling removes pods.
Deleted pods' log directories can still be processed when retained on the PVC.
Repeat with orgb/orgc contexts. A run can include sessions from multiple pods.

## 2. Update the AWS permissions once

The repository policies now include the processed output prefix. Editing a local
JSON file does **not** update IAM. In AWS IAM, edit the permission policy attached
to each `cowrie-uploader-<org>` user using the corresponding
`infra/cowrie/local/uploader-<org>.policy.json`. Keep each policy attached only to
its own organisation's uploader. This adds PutObject on
`<org>/processed/replay/*` while preserving raw upload access.

Update the ML reader's policy from `team-log-reader.policy.json` if that reader
is authorised for all three organisations; otherwise restrict it to its assigned
organisation. This adds GetObject on processed files. No new access keys are
needed when the existing identity's policy is updated. Existing Secrets stay
`cowrie-aws-credentials`; do not put keys in manifests or share uploader keys.

## 3. Build and load the processor

Run from the repository root in PowerShell, with Docker and the kind clusters
running. The image contains the existing shared extractor and schema, and needs
no Torch installation. Rebuild and reload after extractor changes.

```powershell
docker build -f services/log-processor/Dockerfile -t cowrie-log-processor:local-v1 .
if ($LASTEXITCODE -ne 0) { throw 'Image build failed' }
foreach ($org in @('orga', 'orgb', 'orgc')) {
    kind load docker-image cowrie-log-processor:local-v1 --name "$org-honeypot-cluster"
    if ($LASTEXITCODE -ne 0) { throw "Image load failed for $org" }
}
```

This template targets the existing **single-node kind clusters**. Their RWO
local-path PVC can be mounted by Cowrie and this Job on the same node. Do not
use this template unchanged for multi-node/EKS storage.

## 4. Render and review the three jobs

Save the completed selections as `orga.json`, `orgb.json`, `orgc.json` under
`.local/cowrie/replay/`. These files must have their respective organisation.

```powershell
foreach ($org in @('orga', 'orgb', 'orgc')) {
    powershell -NoProfile -ExecutionPolicy Bypass -File deploy/k8s/overlays/local/process-replay.ps1 -Action render -Org $org -Manifest ".local/cowrie/replay/$org.json"
    if ($LASTEXITCODE -ne 0) { throw "Render failed for $org" }
}
```

Review `.local/cowrie/processed-runs/<org>/<run-id>/job.yaml` and
`selection.configmap.json`. `render` does not contact Kubernetes or AWS. Bucket
and region come from that organisation's existing local Kustomization.

## 5. Process and upload

```powershell
foreach ($org in @('orga', 'orgb', 'orgc')) {
    powershell -NoProfile -ExecutionPolicy Bypass -File deploy/k8s/overlays/local/process-replay.ps1 -Action run -Org $org -Manifest ".local/cowrie/replay/$org.json"
    if ($LASTEXITCODE -ne 0) { throw "Run needs inspection for $org" }
}
```

Each run creates an immutable selection ConfigMap and a Job. The processor init
container reads the PVC read-only, without AWS credentials. Only after it
succeeds does the uploader publish the CSV followed by the completion manifest.
The helper waits five minutes; a timeout does not cancel the Job, which has a
30-minute deadline. Inspect it before retrying. Existing run names are rejected.

For example, with `run_id` `replay-001`, the output is:

| Organisation | S3 output folder |
| --- | --- |
| A | `s3://csc3104-cowrie-orga/orga/processed/replay/replay-001/` |
| B | `s3://csc3104-cowrie-orgb/orgb/processed/replay/replay-001/` |
| C | `s3://csc3104-cowrie-orgc/orgc/processed/replay/replay-001/` |

Each folder contains `sessions.csv` and `manifest.json`. S3 prefixes appear when
objects are uploaded; no separate bucket or pre-created folder is needed.

## 6. Hand the completed run to the ML team

Send the run's S3 path, Git revision, and their own reader sign-in/profile setup.
They must require `manifest.json`, verify the CSV's SHA-256 against
`csv_sha256`, and check schema/extractor compatibility before ingestion. Example
using their own reader profile:

```powershell
aws s3 sync s3://csc3104-cowrie-orga/orga/processed/replay/replay-001/ ./data-v2/replay/orga/replay-001/ --profile cowrie-ml-reader
Get-FileHash ./data-v2/replay/orga/replay-001/sessions.csv -Algorithm SHA256
```

CSV columns are the shared extractor's five metadata fields and 16 raw feature
fields. `honeypot` is `orgA`, `orgB` or `orgC`; `session_id` includes organisation,
pod UID and Cowrie session ID. The ML loader applies clipping/log transforms once.
`scan` and `tunnel` rows remain visible but are excluded by the current model.

CSV labels use the same heuristic rules as Kaggle processing. Expected labels
from the replay owner are recorded separately in the manifest, including mismatch
flags. Matching rules is not independent ground-truth validation; the ML team
must inspect replay success and label mismatches before reporting accuracy.

## Duplicate handling and scheduling

Within a run, overlapping full JSON events across files are deduplicated per
pod/session, preserving the largest observed multiplicity of identical events
in one file. This is a heuristic because Cowrie has no universal event ID. It
cannot distinguish two genuinely identical events split across different files.
The manifest records removed counts, source hashes, selections and output hash.

Uploads use conditional PutObject (`If-None-Match: *`) to reject existing keys.
This avoids publishing repeated snapshots under fresh filenames on every timer.
It does not deduplicate the same selected sessions across different run IDs:
the ML consumer must track `(organisation, pod UID, session ID)` across runs.

This selected-replay workflow uses **manual Jobs**. Do not schedule a fixed
selection repeatedly. The local overlays now separately configure the combined
[nightly workflow](cowrie-nightly.md), using persistent checkpoints for all completed
sessions. It does not automatically know which sessions belong to replay.

## Failures and cleanup

Inspect an example run (change organisation/run ID as needed):

```powershell
kubectl --context kind-orga-honeypot-cluster -n default get job cowrie-features-orga-replay-001
kubectl --context kind-orga-honeypot-cluster -n default logs job/cowrie-features-orga-replay-001 -c process
kubectl --context kind-orga-honeypot-cluster -n default logs job/cowrie-features-orga-replay-001 -c upload
kubectl --context kind-orga-honeypot-cluster -n default describe job cowrie-features-orga-replay-001
```

- `ErrImageNeverPull`: load the built image into that kind cluster.
- Pending PVC/volume: verify the existing `cowrie-logs` PVC is Bound in `default`.
- Missing connect/close: correct the selection or wait for replay to finish.
- Malformed/truncated JSON: wait for writers/rotation to settle; the processor
  fails rather than silently dropping bad lines. Frozen file lengths are not a
  transaction across files; avoid rotating/pruning logs during the run.
- AccessDenied: check the live uploader policy's processed prefix and Secret.
- Existing S3 object/precondition failure: inspect the existing run. Never
  overwrite it automatically; use a new run ID after resolving the cause.

CSV and manifest publication is not atomic. If only CSV uploads, the run is
incomplete and consumers must ignore it. A failed Job has no automatic retries;
after diagnosis, use a new run ID. Orphaned objects require deliberate cleanup
by the owner. No local/S3 raw data is deleted by this processor.

Once outputs are verified, the named Job and its ConfigMap may be deleted to
release completed pod resources. Keep S3 outputs and source logs per the team's
retention policy. Do not delete the PVC as cleanup.

Limits: 512 KiB selection, 10,000 sessions, 250,000 selected events, 512 MiB per
source/decompressed file, 1 MiB per JSON line. Split larger batches; large source
files require a reviewed limit change. Output/scratch use bounded emptyDir.

## Development validation

```powershell
python -m unittest discover -s services/log-processor/tests -v
# Existing Kubernetes tests additionally require PyYAML and kubectl.
python -m unittest discover -s deploy/k8s/tests -v
```

Tests use synthetic logs and a fake AWS command. They cover shared feature parity,
selection filtering, incomplete sessions, overlapping rotated logs, immutable
outputs, upload failure ordering, and organisation-specific rendered Jobs.
No live S3 publication is claimed by these tests.
